# ADR-007: API-First 헤드리스 아키텍처 (프론트엔드 교체 가능)

- 상태: ✅ 확정 (2026-07-04)

## Context

요구: "백엔드를 완벽하게 API 형식으로 모듈화·효율화해서, 나중에 프론트엔드를 바꿔도 완벽하게 바꿀 수 있는 느낌으로." 즉 웹앱은 백엔드의 **여러 클라이언트 중 하나**여야 하고, 미래에 데스크톱 앱·모바일·MCP·서드파티 통합이 붙어도 백엔드 재작성이 없어야 한다. (경쟁 제품 중 Presenton/Alai/Plus AI가 API-first로 이 확장성을 확보한 노선)

## Decision

**모든 제품 기능은 `apps/api`의 HTTP/SSE 계약으로만 노출한다. 프론트엔드는 그 계약의 소비자일 뿐 어떤 비즈니스 로직도 소유하지 않는다.**

1. **로직은 packages, 노출은 api, 표현은 web** — 3층 분리:
   - `packages/*`(core/templates/renderer/exporter/research/db): 순수 도메인 로직, HTTP 무지(無知)
   - `apps/api`(Hono): 얇은 라우트 핸들러 — 입력 zod 검증 → 패키지 함수 호출 → 표준 응답. **핸들러에 비즈니스 로직 금지**
   - `apps/web`(TanStack Start): API 호출 + 렌더링만. DB 직접 접근·LLM 직접 호출 절대 금지
2. **계약이 곧 스키마** — 요청/응답/이벤트 타입은 전부 `@im-ppt/schema`(zod)에서 온다. 프론트·백이 같은 타입을 import → 계약 드리프트 불가. (REST는 `docs/03-api/REST_API.md`가 정본)
3. **표준 봉투 고정** — 성공 `{data}` / 실패 `{error:{code,message}}`. 어떤 클라이언트든 동일 파싱.
4. **렌더러는 프레임워크 경계에 유의** — `packages/renderer`는 React지만 "덱 JSON → 화면"의 순수 변환. 웹 특화 상태(라우팅/전역스토어)를 담지 않아, 다른 React 호스트(데스크톱 Electron 등)에 그대로 이식 가능.
5. **stateless API** — 세션 상태는 DB(잡/덱)에 있고 API 인스턴스는 무상태 → 수평 확장·프론트 교체 자유.

### 프론트엔드 교체 시나리오 (검증 기준)

웹앱을 삭제하고 CLI/데스크톱/다른 프레임워크로 재작성해도, `docs/03-api/REST_API.md`의 엔드포인트만 호출하면 **전 기능(생성·게이트·실시간·편집·export·템플릿)이 그대로 동작**해야 한다. 이것이 이 ADR의 수용 테스트.

## Consequences

- (+) 프론트 교체·다중 클라이언트(웹/CLI/MCP/데스크톱)가 백엔드 무변경
- (+) API E2E가 곧 제품 계약 테스트 — 프론트 없이도 전 기능 검증 가능(app.request)
- (+) 오픈소스 사용자가 우리 백엔드 위에 자체 UI를 얹을 수 있음(헤드리스 제품 가치)
- (−) "웹에서만 잠깐" 같은 지름길 금지 — 모든 기능이 API를 거쳐야 함(초기 보일러플레이트↑, 장기 유지보수↓)
- (−) 계약 변경은 스키마 변경 = 프론트·백·문서 동시 갱신 강제(CODING_STANDARDS의 요소 추가 절차와 동일 규율)
